Цель работы и задачи

Цель работы — изучить модель программирования ASP.NET Core Razor Pages и перевести учебное приложение учёта грузов с MVC на Razor Pages, а затем подготовить его к публикации в контейнере.

Задачи

  1. Разобрать структуру Razor Pages: страница .cshtml и её PageModel.
  2. Реализовать обработчики OnGet() и OnPost(), привязку модели через [BindProperty].
  3. Реализовать полный CRUD: каталог, добавление, просмотр, редактирование и удаление груза.
  4. Добавить поиск, фильтрацию, серверную и клиентскую валидацию, уведомления через TempData.
  5. Оформить интерфейс на Bootstrap 5 с единым адаптивным layout.
  6. Собрать Docker-образ, опубликовать приложение на Render, оформить Git-репозиторий и отчёт.

Домен и функциональность

CargoFlow автоматизирует базовый учёт грузов на складе. Основная сущность — Cargo (груз), перенесённая из лабораторной работы WT-4. Для каждой позиции хранятся название, категория, количество, место хранения, вес одной единицы, описание и признак доступности.

Общий вес партии и текстовый статус не дублируются в хранилище, а вычисляются в модели. Данные находятся в едином статическом хранилище CargoStore, поэтому добавленные записи видны на всех страницах до перезапуска приложения.

Модель данных05 / 27

Модель Cargo

Модель описывает груз и одновременно задаёт правила валидации через DataAnnotations. Те же атрибуты [Display] используются Tag Helpers для подписей полей формы.

Рис. 1. Models/Cargo.cs — модель, атрибуты валидации и вычисляемые свойства

Что важно в модели

  • [Required], [StringLength] и [Range] задают серверные правила и автоматически попадают в клиентскую валидацию.
  • [Display(Name = ...)] даёт русские подписи полей без дублирования текста в разметке.
  • TotalWeight и Status вычисляются на лету — в хранилище хранятся только исходные данные.
  • Модель не зависит от Razor Pages и может быть повторно использована в другом типе приложения.

Хранилище06 / 27

Единое хранилище CargoStore

В лабораторной работе не требуется база данных, поэтому используется статический список в памяти. Он общий для всех PageModel: страница добавления записывает объект, а каталог и главная сразу видят изменение.

Рис. 2. Data/CargoStore.cs — стартовый набор грузов и общий список

Как устроено хранилище

  • static class CargoStore содержит единственный List<Cargo> на всё приложение.
  • При старте добавляются 6 реалистичных грузов разных категорий — интерфейс не пустой.
  • GetNextId() возвращает максимальный Id + 1, поэтому новые записи не конфликтуют.
  • После перезапуска приложения пользовательские записи исчезают — это осознанное ограничение учебного проекта.
Ограничение Хранилище не потокобезопасно и не сохраняется на диск. Для учебного сценария этого достаточно; в production здесь была бы база данных и репозиторий с внедрением зависимостей.

CreateModel: [BindProperty] и OnPost()

Форма добавления — центральный сценарий работы. Свойство Cargo помечено [BindProperty], поэтому ASP.NET Core автоматически связывает поля POST-запроса с моделью до вызова OnPost().

Рис. 5. Pages/Cargo/Create.cshtml.cs — привязка модели и обработчик POST

Ключевые решения

  • ModelState.IsValid — единая точка проверки серверной валидации; при ошибке возвращается та же страница.
  • Id выдаётся хранилищем, а строковые поля очищаются от пробелов через Trim().
  • TempData["SuccessMessage"] переживает редирект и показывает одноразовое уведомление.
  • RedirectToPage("./Index") реализует паттерн Post/Redirect/Get — форма не отправляется повторно при обновлении.

Форма добавления груза

Форма собрана на Tag Helpers: они генерируют корректные name/id, подставляют значения, подписи и атрибуты клиентской валидации. Отдельный partial подключает jQuery Validation.

Рис. 6. Pages/Cargo/Create.cshtml — поля формы, asp-for и вывод ошибок

Tag Helpers в форме

  • asp-for="Cargo.Name" связывает input со свойством и добавляет data-val-* атрибуты.
  • asp-validation-for выводит сообщение конкретного поля, asp-validation-summary="ModelOnly" — общие ошибки.
  • asp-items="Model.Categories" заполняет выпадающий список категорий.
  • <partial name="_ValidationScriptsPartial" /> включает клиентскую проверку до отправки формы.
Доступность У полей есть label, подсказки placeholder, обязательные поля отмечены звёздочкой, а кнопки имеют понятные тексты — форма удобна и с клавиатуры.

Просмотр и удаление

Страница подробностей принимает id из query string и возвращает NotFound(), если запись не найдена. Удаление сделано в два шага: OnGet показывает подтверждение, OnPost удаляет запись.

Рис. 8. Обработчики Details.OnGet(int id) и Delete.OnPost(int id)

Почему удаление через POST

  • GET-запрос не должен изменять состояние — иначе удаление сработает по простой ссылке или предзагрузке.
  • Страница подтверждения показывает название груза, чтобы пользователь не удалил запись случайно.
  • После удаления выполняется RedirectToPage("./Index") и показывается сообщение через TempData.
  • Для отсутствующего id возвращается NotFound(), а не пустая страница.

Подробности и удаление

Карточка подробностей показывает все поля груза, включая вычисленные общий вес и статус. Удаление требует явного подтверждения и показывает, какая именно запись будет удалена.

Рис. 14. Подробная карточка груза
Рис. 15. Подтверждение удаления

Сценарии

  • «Подробнее» открывает /Cargo/Details?id=… и показывает полную информацию о грузе.
  • «Редактировать» открывает форму с уже заполненными полями.
  • «Удалить» открывает страницу подтверждения; фактическое удаление выполняется POST-запросом.

MVC и Razor Pages

Razor Pages не является отдельным фреймворком: это модель организации приложений ASP.NET Core, которая использует ту же маршрутизацию, middleware, DI, Razor и Tag Helpers. Отличается способ группировки кода страницы.

АспектASP.NET Core MVCRazor Pages
Единица организацииController + Action + ViewСтраница + PageModel
Обработчик запросаМетод контроллераOnGet() / OnPost()
РасположениеControllers/ + Views/Pages/ — рядом
Привязка формыПараметры action или модель[BindProperty]
РедиректRedirectToAction()RedirectToPage()
МаршрутАтрибуты / шаблоны контроллераПуть файла страницы
РазметкаRazor ViewRazor Page
Хорошо подходитКрупные API и сложные сценарииСтраничные сценарии, CRUD, формы

Вывод по сравнению

Для приложения с преобладанием страничных сценариев Razor Pages оказался компактнее: код страницы и её обработчики находятся в одном месте, не нужно создавать отдельный контроллер и представление, а имена обработчиков напрямую отражают HTTP-метод.

MVC остаётся удобнее там, где много общих API-действий, сложная маршрутизация или несколько представлений на один контроллер. В нашем CRUD-приложении Razor Pages дал более простую структуру при сохранении всех возможностей ASP.NET Core: валидации, Tag Helpers, DI и middleware.

Когда что выбирать

СитуацияРекомендация
Страничные CRUD-сценарии и формыRazor Pages — код страницы и обработчик рядом
Крупный API с множеством endpoint’овMVC-контроллеры или Minimal API
Одна страница — несколько представленийMVC: контроллер управляет выбором View
Быстрый старт небольшого сайтаRazor Pages: меньше файлов и связующего кода
